Part 1 — Concepts

1.1 Workspace hierarchy

The Builder Studio organises everything a user builds inside a single Workspace. The persistent model, defined in stores/workspace-store.js, forms a four-level tree.

LevelWhat it isSideNav location
WorkspaceTop-level container. One per app install; seeded as Default with id ws_default.Workspace switcher (top-left of SideNav).
TeamLogical grouping of agent pools owned by a squad. The seed ships with one team — fullstack builders.SideNav → Teams section, click to open TeamEditor.
Agent PoolA roster of related agents that collaborate (e.g. the default pool holds the URL extractor + summariser).Nested inside each team card. Click the pool row to expose its agents.

SkillA reusable JavaScript (or Python) function stored alongside the workspace. Skills have a source body, an inputSchema, and an outputSchema. Agents attach skills via attachedSkillIds.SideNav → Skills. Opens SkillEditor.
WorkflowA canvas of nodes + edges + subBlockValues. Each workflow belongs to a team and has metadata (timeout, retries, failFast, logLevel, tags) surfaced in the WorkflowInspector.SideNav → Workflows. Click to load it into the canvas.

Agents and skills are referenced by id from workflow nodes — editing an agent in one place propagates to every workflow that cites it. Teams are pure organisational units: they don't execute anything, but they scope which agent pools (and therefore which agents) surface in the block inspector's combo boxes.

1.2 Workflow execution model

run/graph-runner.js drives every run in the browser. The algorithm is a topological BFS with readiness gating:

  1. Seed phase. Every starter node's output is set to null; every user_input node's output is set to the value the Run dialog collected (or its defaultValue). Both are marked started and emit start+done events so their cards turn green on the canvas.
  2. Ready set. A node is ready when every incoming edge is "live": its source has finished and either the source is a single-output block or the edge's sourceHandle matches the chosenHandle the source picked. Branching nodes (if_else, if_elseif_else, switch) record their chosen handle here; non-matching edges are silently skipped.
  3. Concurrent dispatch. All ready nodes are awaited via Promise.all. Siblings run in parallel; chains stay sequential because a downstream node blocks on the upstream's output.
  4. Per-node execution. runNode() switches on blockType. Pure control-flow and utility blocks execute locally; the only type that currently hops to the convengine backend is agent (POST /api/v1/builder-studio/agent).
  5. Output shape. Most blocks return a raw value. Agent (and MCP) nodes return { __meta, value }; the runner unwraps value onto outputs[nodeId] and keeps __meta on the trace row + the onProgress done event. Branching blocks return { branch, value } — the runner stores the chosen handle on chosenHandle[nodeId] and forwards the payload only along edges leaving that handle.
  6. Final output. When no more nodes become ready, the runner returns { output, trace } where output is the response node's output if present, otherwise the last trace row's output.

Templating

Agent nodes build a template bag — an object seeded with { input } (plus { url } when the upstream looks like an HTTP URL), extended with every key of the upstream JSON if the upstream is an object, and further extended with each executed skill's return value. interpolateBag() then substitutes {{key}} tokens in systemPrompt and userPrompt. Unresolved tokens are left verbatim so typos show up in the Debug panel.

response nodes use a simpler interpolate() that substitutes {{input}} and <nodeId.output> references against the outputs map.

Agent call envelope

The { __meta, value } contract is what powers the rich Debug panel: every agent run records the rendered system and user prompts (i.e. post-templating), the model, temperature, the list of skill ids attached, the per-skill call log (skillRuns — one entry per skill with { skillId, name, params, output } or { error }), and the raw agent provider response. The Inspector surfaces values (what the user authored) alongside meta (what actually ran), which is invaluable for spotting "why did my prompt look different at runtime?" bugs.

1.3 Run dock panels

The bottom Run Dock aggregates four panels. They share the same onProgress event stream emitted by the graph runner:

PanelWhat it shows
OutputThe final result.output formatted with JsonView. Monaco-style colorisation: indigo keys, green strings, amber numbers, pink booleans.
DebugA chronological event log: one card per start, done, or error. Each card can be expanded; expanded cards reveal the full values, rendered prompts from meta, skillRuns, and the raw provider response.
TraceA grid, one row per node, columns: title · blockType · input · values · meta · output · ms. Clicking a cell opens a JSON viewer. This is the fastest way to spot which node took too long or produced unexpected output.
ConsoleEphemeral console.log capture from function and skill executions (via the stdout output channel on the Function block).

Every node card on the canvas has one of four visible states: idle (default), active (dashed pulsing green border, triggered on start), completed (solid green border with check, triggered on done), or error (red ring + tooltip showing error.message, triggered on error).

1.4 Inspector

panel/Inspector.jsx renders the right rail. When a node is selected it looks up the BlockConfig via getBlock(blockType) and walks cfg.subBlocks. Each sub-block is passed to SubBlockRenderer.

Basic vs advanced tabs. The header shows a mode pill row when any sub-block has mode: 'advanced' (or 'trigger-advanced'). The visibleSubBlocks memo filters by the active mode (matchesMode) plus the field-level condition predicate (conditionPasses). A condition can be { field: 'x', value: 'y' }, { field: 'x', value: ['a','b'] }, or { field: 'x', value: '', not: true } for "visible when x is non-empty".

Delete-with-confirm. The trashcan icon on the header opens a ConfirmModal; only after accept does removeNode(selectedNodeId) fire.

About icon / docs overlay. A question-mark button toggles BlockDocViewer, which reads hand-written entries from docs/block-docs-entries.js (field descriptions, tips, alerts). This is the source of truth for inline docs; the block source files only carry a shallow description.

FullscreenWrapper. Response Format fields (type response-format) render through FullscreenWrapper → JsonEditor so large JSON Schemas can be edited against the full viewport without fighting the narrow inspector column. Edits stay as a stringified JSON in subBlockValues so the backend contract is unchanged.

IOPanel. At the bottom of the inspector, an I/O panel (panel/io-registry.js) summarises the node's connections (incoming/outgoing edges with peer titles), template variables (every {{foo}} token found in systemPrompt / userPrompt / data fields), and the typed inputs + outputs lifted from cfg.inputs and cfg.outputs. Template variables that don't resolve to an upstream key or a skill output are flagged with a yellow warning chip.

1.5 Extensions pattern

Third-party blocks live in convengine-ui/src/builder-studio/extensions/*.js. Registry (blocks/registry.js) uses Vite's import.meta.glob to eagerly load every extension at boot. Each module must expose either a default BlockConfig or a named block / <Name>Block export. Any type id that collides with a core block is rejected with a console warning.

A minimal custom block (see Appendix §4.3 for a full example) exports something like: 

export const MyCounterBlock = {
  type: 'my_counter',
  name: 'Counter',
  description: 'Increments a counter',
  category: 'blocks',
  bgColor: '#64748b',
  icon: () => null,
  subBlocks: [
    { id: 'start', title: 'Start', type: 'short-input', defaultValue: '0' },
  ],
  tools: { access: [] },
  inputs: { start: { type: 'number', description: 'Starting value' } },
  outputs: { value: { type: 'number', description: 'Incremented value' } },
}
export default MyCounterBlock

Drop the file, refresh, and the toolbar auto-discovers it. The manual alternative — registerBlock(block) — mirrors ComfyUI's registerNode API for URL-loaded plug-ins.

Part 2 — Block reference

Each block is documented from its source in blocks/blocks/*.js plus the inline docs in docs/block-docs-entries.js. Control mappings reference SubBlockRenderer.jsx. "Execution notes" are what graph-runner.js does when the node fires.

Blocks are listed in the exact order of blocks/blocks/index.js.

What it does. The entry point of every workflow. Defines how the workflow is launched (manual vs chat) and optionally an Input Format schema for structured manual test runs. Hidden from the toolbar because it is added automatically on workflow creation.

Execution notes

  1. Skill ids are parsed from values.skills (and legacy values.tools).
  2. The bag is seeded; inputStr is JSON-stringified if not a string.
  3. Each skill runs via new Function('params', skill.source); its output replaces inputStr and, if object-shaped, merges into the bag.
  4. systemPrompt and userPrompt are templated via interpolateBag.
  5. POST /api/v1/builder-studio/agent → { __meta, value }. value is the LLM's output string (or parsed JSON when strict).
Tip. Prefer attaching skills here over creating separate integration blocks; only move to a dedicated block when you need full determinism over the API call.
Warning. strictOutput only fires when responseFormat is set. Not every provider + model combination supports strict mode.

Gotchas

  • The backend currently drops unknown fields — anything outside model, systemPrompt, userPrompt, responseFormat, strictOutput is ignored server-side. Skills are why the runner executes them client-side.
  • Template tokens that don't resolve are left verbatim; check the rendered prompt in the Debug panel's meta.userPrompt before blaming the model.

Function function blocks

What it does. Runs arbitrary JavaScript or Python. In the Builder Studio runtime the code is wrapped as new Function('input', 'values', src) and executed in-browser; Python routing exists in the schema but is handled server-side in production deployments.

Inputs

keytypedescription

Outputs

Fields

idtitlecontrolrequiredvisible whendefaultwhat it does
languageLanguagedropdown—alwaysjavascriptChooses the runtime.
codeCodeCodeMirror (javascript)—always—Function body. Has access to input and values. Must return the downstream payload. Wand icon generates from NL.

Execution notes

runFunctionNode does new Function('input', 'values', src)(input, values). No sandbox. The return value becomes outputs[nodeId].

Security. Because the code runs in the user's browser with full DOM access, Function blocks should never execute untrusted source. If you host a shared builder, proxy these through a server sandbox.

Gotchas

  • No async wrapper by default — if you need to await fetch(), wrap your body with return (async ()=> { … })().
  • Reference upstream data via the input arg; the alternative <blockName.output> placeholder syntax is only honoured in the Response block.

}

A · Seeded · URL → Summary

Goal. Paste a URL, have a skill fetch & strip the page, then an LLM summarise it in 3–5 bullets. Ships pre-seeded as wf_demo_url_summary.

When you'd use it. Any time you need to fetch-and-summarise third-party content. Swap the final agent's prompt to repurpose (translate, classify, extract entities, etc.).

Node-by-node

  • n_starter (starter) — emits null, flips green.

4.3 Writing a custom block

Two steps: write a BlockConfig, drop it in builder-studio/extensions/. The registry auto-discovers it on the next dev-server reload.

// convengine-ui/src/builder-studio/extensions/slugify.js
import { VariableIcon } from '../components/icons'

export const SlugifyBlock = {
  type: 'slugify',                // must be unique; can't shadow core
  name: 'Slugify',
  description: 'Normalise a string to a URL slug',
  category: 'blocks',
  bgColor: '#64748b',
  icon: VariableIcon,
  subBlocks: [
    {
      id: 'lowercase',
      title: 'Lower-case',
      type: 'switch',
      defaultValue: true,
    },
    {
      id: 'separator',
      title: 'Separator',
      type: 'short-input',
      defaultValue: '-',
    },
  ],
  tools: { access: [] },
  inputs:  { input: { type: 'string', description: 'String to slugify' } },
  outputs: { result: { type: 'string', description: 'Slugified output' } },
}

export default SlugifyBlock

For branching behaviour, add outputHandles or outputHandlesFromValues(values). To implement the block's runtime, add a case to graph-runner.js's runNode switch (or, for production extensions, wire a small adapter module that patches the registry + runner at boot).

To register at runtime (e.g. from a user-supplied URL), call registerBlock(block); listeners subscribed via onRegistryChange() re-render the toolbar.

4.4 Troubleshooting

Symptom in the Debug panelLikely cause & fix
"No content provided to summarize" (or similar LLM refusal) Template variable didn't resolve. Expand the row, inspect meta.userPrompt — if you see literal {{foo}}, the key wasn't in the bag. Upstream must emit a JSON object or a URL, and foo must appear either as a top-level key or as the input alias.
"MCP block: arguments is not valid JSON — Unexpected token …" The arguments JSON is malformed (often caused by raw quotes inside a {{input}} replacement). Wrap the {{input}} in an explicit string context: {"query": "{{input}}"} instead of "{{input}}" alone.
Node stays "active" forever A preceding branch block didn't pick a live edge. Open the Trace panel and check if the upstream's chosenHandle matches any outgoing edge's sourceHandle. If not, add an else / default branch or fix the expression.
"TypeError: fn is not a function" from a Function block The code body isn't an expression that evaluates to a value. Wrap it with return …. Remember: it's a body, not an arrow function — plain statements + a return.
Skill output ignored; agent still sees the raw URL The field is values.skills, not values.tools (both are accepted, but the Inspector writes to skills). Confirm the node's subBlockValues has a skills JSON array with valid ids.
Response Format schema ignored Both responseFormat must be set AND strictOutput must be on to get provider-enforced JSON. Without strict mode, some models will produce drift; turn it on in the Agent's advanced tab.
"Invalid JSON data format: …" from PostgreSQL insert The data field is not valid JSON. Open the editor (JSON tree) and fix the offending row.
CORS errors on the demo's URL extractor skill fetch() is subject to CORS; most docs sites permit cross-origin GET but some don't. Either proxy the request through the convengine backend or switch to the API block which goes server-side.
Nothing runs on Run — dock shows no trace No starter/user_input exists. The BFS has no seed nodes. Every workflow needs at least one of those two types to produce a ready set.
"Extension at … tried to overwrite core block" in console An extension's type collides with a core id. Pick a different id; the registry rejects overwrites to prevent accidental shadowing.
Reading material. DEMO_WALKTHROUGH.md reproduces the seeded workflow step-by-step. For the authoritative field list on any block, look at blocks/blocks/<name>.js; for the authoritative field copy, look at docs/block-docs-entries.js.
